# 성능 관찰성(Observability) 인프라

<!-- 앞으로의 모든 개발에서 성능을 지속적으로 측정·기록·검증하는 체계 -->

## Problem

현재 성능 문제가 반복적으로 지적되지만:
- 매번 수동으로 Playwright로 측정해야 함
- 프로덕션에서 실제 사용자가 겪는 지연을 알 수 없음
- 새 기능 추가 시 성능 회귀(regression)를 감지할 방법이 없음
- QA가 성능을 체크하려면 기준(budget)이 없음

## Solution — 3계층 관찰성

### 1. 클라이언트 메트릭 수집 (실사용자 체감)

**Web Vitals + 커스텀 메트릭을 Supabase에 기록:**
- LCP (Largest Contentful Paint) — 페이지가 의미있게 보이기까지
- FID/INP (Interaction to Next Paint) — 탭 클릭 → 반응까지
- 페이지 전환 시간 — 탭 A → 탭 B 완료까지
- 각 메트릭에 페이지 경로, 유저 ID, 타임스탬프 포함

### 2. 서버 사이드 쿼리 로깅

**각 페이지 렌더링 시 쿼리 시간 기록:**
- Server Timing 헤더에 각 쿼리 이름과 소요 시간 포함
- 예: `Server-Timing: auth;dur=45, profile;dur=32, season;dur=28, workouts;dur=110`
- 프로덕션에서 DevTools Network 탭으로 즉시 확인 가능
- 느린 쿼리(200ms+) 자동 로깅

### 3. 성능 예산(Budget) + CI 검증

**각 페이지별 성능 예산 정의:**
| 페이지 | 서버 응답 예산 | loading.tsx 필수 |
|---|---|---|
| /records | 800ms | ✅ |
| /penalty | 600ms | ✅ |
| /stats | 600ms | ✅ |
| /settings | 500ms | ✅ |
| /workout/new | 400ms | ✅ |

**개발 규칙 (CLAUDE.md에 반영):**
- 새 페이지는 반드시 `loading.tsx` 포함
- 한 페이지당 순차 Supabase 호출 최대 2단계 (auth → 나머지 전부 Promise.all)
- 공통 데이터(`getUser`, `getProfile` 등)는 반드시 `src/lib/data.ts`의 캐시 함수 사용
- 새 쿼리 추가 시 Server Timing에 등록

**CI 성능 테스트:**
- `test/perf.test.ts` — 각 페이지 응답시간이 budget 내인지 검증
- 로컬 dev 서버 기준, CI에서 자동 실행

## Scope

**Includes:**
- `performance_log` Supabase 테이블 (메트릭 저장)
- 클라이언트 Web Vitals 수집 컴포넌트
- 서버 쿼리에 Server Timing 헤더 추가
- 성능 예산 정의 + CI 테스트
