# 성능 측정·분석·최적화 체계

<!-- 모든 페이지의 응답 시간을 측정하고, 원인을 분석하고, 체계적으로 최적화한다 -->

## Problem

탭 전환마다 400~700ms(로컬), 프로덕션은 더 느림. 매 탭 클릭이 서버 풀 왕복이고 로딩 UI가 없어서 "멈춤"으로 느껴짐. 성능을 측정하는 구조도 없어서 개선 여부를 판단할 수 없음.

## Root Cause Analysis

### 병목 1: 레이아웃 중복 쿼리
- `(app)/layout.tsx`가 매 요청마다 `getUser()` + `profiles.select()` 실행
- 각 페이지도 동일한 `getUser()` + `profiles` 쿼리를 다시 실행
- **같은 요청 내 2~3회 중복 DB 호출**

### 병목 2: 로딩 UI 부재
- 서버 응답 올 때까지 이전 화면이 정지 상태로 유지
- 사용자는 "탭이 안 눌림" "멈춤"으로 인식
- 실제 400ms인데 체감 2초+

### 병목 3: 캐싱 없음
- 벌금, 통계 등 자주 변하지 않는 데이터도 매번 fresh 쿼리
- 같은 시즌, 같은 주의 데이터를 탭 전환할 때마다 다시 조회

### 병목 4: 서버 컴포넌트 폭포
- layout getUser → page getUser → page queries → 순차 실행
- Promise.all로 병렬화한 부분도 있지만, layout↔page 간은 순차

## Solution

### 1. 즉시 로딩 UI (가장 큰 체감 개선)
- 각 라우트에 `loading.tsx` 추가 — 스켈레톤 UI
- 탭 클릭 즉시 스켈레톤 표시 → 데이터 도착 시 교체
- **체감: "멈춤" → "로딩 중"으로 전환**

### 2. 쿼리 중복 제거
- `React.cache()`로 같은 요청 내 getUser/getProfile 결과 재사용
- layout과 page가 같은 캐시된 함수를 호출 → DB 왕복 절반으로

### 3. 데이터 캐싱 (Next.js unstable_cache)
- 시즌 정보, 크루 멤버 목록: 5분 캐시 (거의 변하지 않음)
- 워크아웃 데이터: 30초 캐시 (인증 등록 후 revalidate)
- 벌금 계산: 30초 캐시

### 4. 성능 측정 인프라
- Server Timing 헤더로 각 쿼리 시간 기록
- 클라이언트에서 페이지 전환 시간 측정 (Web Vitals)
- `/api/health` 엔드포인트: DB 연결 + 쿼리 응답시간 체크

## Scope

**Includes:**
- 모든 라우트에 loading.tsx (스켈레톤 UI)

- 공통 데이터 함수 캐싱
